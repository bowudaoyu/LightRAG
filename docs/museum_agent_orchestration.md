# Agent 编排层设计

> 本文档定义 Agent 编排层的架构设计，记录了从串行方案到最终方案的演进过程和决策依据。

## 一、方案演进：从串行到并行到最终架构

### 1.1 初始方案：串行 4 轮检索（已否决）

最初设计 Agent 做 4 轮串行检索（R1 骨架 → R2 事件 → R3 风险 → R4 丰富），存在两个根本问题：

**问题 1：延迟不可接受**

4 次串行 LightRAG 检索 + 最终 LLM 生成，总延迟约 `4R + P`。假设单次检索 2s、生成 3s，总计 ~11s。

**问题 2：骨架先行假设是错误的**

原方案假设"先定骨架再叠加细节"，但动态事件可能**推翻骨架本身**。

**反例**：假设 F3 南区 9:00 有庞贝策展人导览，B1 北区 10:00 有青铜器讲解。

- 如果 R1 先定骨架 → "B1 起步逐层上升"
- R2 发现 F3 的 9:00 讲解 → 但骨架已经安排 B1 先行，来不及
- 最优路线其实是 **F3→…→B1**（从顶层往下走），但串行方案无法回溯修改骨架

**本质**：事件不是"叠加在骨架上的装饰"，而是**重塑骨架的硬约束**。

**根因**：4 轮 R1→R2→R3→R4 把检索和编排混为一体，但实际上：
- **检索之间没有数据依赖** —— "3小时精华路线"和"今天有什么活动"可以同时查
- **编排必须看到全貌才能决策** —— 路线方向、时间分配、站点取舍必须在所有候选数据到齐后一次性规划

### 1.2 中间方案：并行检索 + 纯代码编排（已否决）

将检索和编排分成两个阶段：

```
Phase 1: 并行检索（4 个 aquery_data 并行发出）→ Phase 2: 代码编排算法 → Phase 3: LLM 生成文案
```

解决了串行方案的两个问题，但引入新的问题：
- 代码编排算法（提取锚点 → 排时间线 → 填空隙 → 附 Story）是**硬编码逻辑**
- 几万家博物馆不可能逐一定制编排代码
- 代码做"路线创意"和"个性化推荐"的能力远不如 LLM

### 1.3 另一个候选：全部依赖 LightRAG（已否决）

把编排能力也放到 LightRAG 内部，通过精心设计 query 和 user_prompt，一次 `aquery()` 调用完成检索 + 规划 + 生成。

这个方案最简单（代码量最少、LLM 调用次数最少），但在三个维度的综合评估中不够理想。详见第二节。

## 二、方案对比：全部依赖 LightRAG VS 单独编排 Agent

从三个维度评估，附加约束条件：
- **效果**：必须最好，考虑个性化，让用户觉得"活的，太神了"
- **扩展性**：面向全球几千到几万家博物馆
- **延迟**：必须 < 10 秒

### 2.1 效果维度

"用户觉得太神了"的四个要素：
- **精准**：时间算对（"9:05到，9:55集合，10:00讲解"）
- **周全**：不会让用户走到关门的展厅
- **个性化**：带老人跳过爬楼、带孩子加入亲子活动
- **有惊喜**：看完后母戊鼎顺口说"今晚国家宝藏讲这件鼎"

| 要素 | 全部 LightRAG | 单独 Agent |
|------|:---:|:---:|
| 精准（时间算术） | **弱** — LLM 连续时间计算容易累计误差，且无校验环节 | **强** — 代码计算 100% 精确 |
| 周全（风险覆盖） | **中** — 单次查询可能漏掉语义跨度大的 Notice（如"电梯维修"与"路线规划"语义距离远） | **强** — 多个针对性查询确保每类数据被覆盖 |
| 个性化 | **弱** — 用户画像塞进 query 会干扰检索意图（"带6岁孩子"导致检索偏向亲子内容，挤掉路线信息） | **强** — 检索阶段用画像过滤，规划阶段用画像调权重，生成阶段用画像调语气，三层各取所需 |
| 惊喜感 | **强** — LLM 擅长发现 context 中的隐藏关联 | **取决于实现** — 如果 Agent 用 LLM 做软决策则同样好 |

**效果结论**：单独 Agent 在精准和周全上明显更好，但 Agent 的规划逻辑如果纯代码则缺乏灵活性。

### 2.2 扩展性维度

从单馆扩展到全球几万家博物馆的核心挑战：

| 挑战 | 全部 LightRAG | 单独 Agent |
|------|:---:|:---:|
| 大馆（上万展品） | **弱** — top_k=80 覆盖不足，开大 top_k 撑爆 context | **强** — 根据馆规模动态调整查询数量和 top_k |
| 跨馆场景 | **弱** — 单次 aquery 只能查一个 workspace | **强** — Agent 管理多个 workspace，做跨馆规划 |
| 异构数据 | **弱** — 有的馆有 Route 模板、有的没有，单一 prompt 难适配 | **中** — 代码硬编码同样难适配；LLM 驱动的 Agent 更好 |
| 多数据源 | **弱** — 只能用 LightRAG 存的数据 | **强** — 可接入实时客流 API、天气 API、用户历史 DB |

**扩展性结论**：Agent 层明显更好，但 Agent 的规划逻辑不能是硬编码的——必须 LLM 驱动才能泛化。

### 2.3 延迟维度

```
全部 LightRAG:
  1×关键词提取(~1s) + 1×检索(~1s) + 1×LLM生成(~3-4s) = ~5-6s ✅

轻量 Agent:
  N×关键词提取(并行~1s) + N×检索(并行~1s) + 代码(~0.1s) + 1×LLM生成(~3-4s) = ~5-6s ✅

重量 Agent（多轮推理）:
  检索(2s) + LLM规划(3s) + 校验冲突 + 再检索(2s) + LLM修正(3s) = ~10s+ ❌
```

**延迟结论**：两种方案都能在 10s 内完成，前提是 Agent 不做多轮迭代。

### 2.4 综合评估

| 维度 | 全部依赖 LightRAG | 纯代码 Agent | LLM 驱动的轻量 Agent |
|------|:---:|:---:|:---:|
| 效果-精准 | 弱 | 强 | **强**（代码做硬逻辑） |
| 效果-惊喜 | 强 | 弱 | **强**（LLM 做软决策） |
| 效果-个性化 | 弱 | 强 | **强**（分层处理） |
| 扩展性 | 弱 | 中（硬编码不泛化） | **强**（LLM prompt 泛化） |
| 延迟 | 优 5-6s | 优 5-6s | **优 5-6s** |
| 代码复杂度 | 极低 | 高 | 中 |

**最终结论**：两个纯方案都不是最优。正确答案是 **LLM 驱动的轻量 Agent + LightRAG 纯检索**。

## 三、最终架构：LLM 驱动的轻量 Agent

### 3.1 核心原则

**代码做硬逻辑，LLM 做软决策。**

| 能力 | 谁做 | 为什么 |
|------|------|--------|
| 向量检索 + 图遍历 | LightRAG | 这是它的核心能力 |
| 时间算术、冲突检测、回头路检测 | Agent 代码 | 代码 100% 精确，LLM 会算错 |
| 路线规划 + 个性化 + 内容编排 + 文案生成 | Agent LLM | LLM 擅长软决策，且能泛化到任何博物馆 |
| 结果校验 | Agent 代码 | 兜底，防止 LLM 幻觉 |

**为什么不全用代码做规划**：几万家博物馆，每家数据结构和特色不同，硬编码规划逻辑无法泛化。LLM 读懂数据自行推理，换博物馆只需换 workspace 不改代码。

**为什么不全用 LLM 做规划**：LLM 算"10:45 + 5分钟移动 + 15分钟参观"可能算出 11:10 而不是 11:05。时间算术、冲突检测这些确定性逻辑必须用代码保证正确。

### 3.3 Step 2 详细设计：并行检索

LightRAG 的 `aquery_data()` 方法返回结构化数据（entities, relationships, chunks），不触发 LLM 生成。

LightRAG 完全支持并发查询：`aquery()` 是纯 async 方法，查询路径无锁，可直接 `asyncio.gather()` 并行。多用户请求之间也是并发的，不需要等一个用户查完才能查下一个。

```python
# 所有查询并行发出
results = await asyncio.gather(
    rag.aquery_data(
        "3小时 首次 国宝 精华路线",
        param=QueryParam(mode="mix", top_k=60, chunk_top_k=20)
    ),
    rag.aquery_data(
        f"{today} 活动 讲解 导览 体验",
        param=QueryParam(mode="mix", top_k=40, chunk_top_k=15)
    ),
    rag.aquery_data(
        f"{today} 关闭 维修 限流 排队 注意",
        param=QueryParam(mode="mix", top_k=40, chunk_top_k=15)
    ),
    rag.aquery_data(
        "咖啡 文创 冷知识 打卡 拍照 纪念品",
        param=QueryParam(mode="mix", top_k=40, chunk_top_k=15)
    ),
)

# 每个 result 的结构:
# {
#   "status": "success",
#   "data": {
#     "entities": [...],        # 实体列表 (name, type, description, source_id, file_path)
#     "relationships": [...],   # 关系列表 (src_id, tgt_id, description, weight, file_path)
#     "chunks": [...]           # 文本块 (content, file_path, chunk_id)
#   },
#   "metadata": {...}
# }
```

**查询数量的自适应策略**：

| 博物馆规模 | 节点数 | 查询策略 | 理由 |
|-----------|:------:|---------|------|
| 小馆 | < 200 | 1 次宽查询 | 一次 top_k=80 就能覆盖全部 |
| 中馆 | 200-2000 | 2-4 次针对性查询 | 语义跨度大，需要分类检索保证覆盖 |
| 大馆 | > 2000 | 4-8 次针对性查询 | 数据量大，需要更精准的 file_path 过滤 |

### 3.4 Step 3 详细设计：LLM 规划 + 生成

这是整个系统最关键的一步。LLM 接收全部结构化检索结果 + 用户画像，一次性完成规划和文案生成。

**为什么 LLM 能做好规划**：
- 博物馆锚点通常 < 5 个，约束 < 5 个，站点 < 15 个——这个规模 LLM 完全能推理
- LLM 擅长的是"理解意图、匹配兴趣、发现关联、生成自然语言"——这正是规划需要的软决策
- 相比硬编码算法，LLM 能泛化到任何博物馆，不需要为每家馆定制代码

**Prompt 设计**：

```python
PLANNER_SYSTEM_PROMPT = """你是博物馆AI导游「全能逛馆搭子」。
你的任务是根据检索到的博物馆数据，为用户生成一份完整的参观攻略。

## 规划原则

1. **时间锚点优先**：识别有固定时间的活动（讲解、导览、工作坊）作为锚点，围绕锚点决定路线方向和节奏。不要先定路线再插活动——应该先排锚点再连路线。
2. **约束硬性遵守**：闭馆时段、设施维修等约束必须绝对遵守，不能安排用户在闭馆时到达。
3. **受众匹配过滤**：根据用户画像过滤不匹配的活动（如无儿童则跳过亲子活动）。
4. **空间连续性**：避免走回头路，利用楼层上下关系优化动线。
5. **个性化调整**：有老人→减少步行和爬楼、增加休息；有儿童→加入互动体验；兴趣偏好→相关展区多花时间。
6. **惊喜注入**：每个站点附上相关的冷知识、拍照tips、文创推荐，让体验超出预期。
7. **时间留白**：不要把时间排满，留 10-15% 的弹性给拍照、上厕所、意外发现。

## 输出要求

同时输出两部分：

### Part 1: Plan JSON（用于系统校验）
```json
{
  "stops": [
    {
      "zone_id": "...",
      "zone_name": "...",
      "arrive_time": "HH:MM",
      "depart_time": "HH:MM",
      "duration_min": N,
      "anchor_event": "活动名称 or null",
      "artifacts": ["文物1", "文物2"],
      "notices": ["注意事项"],
      "stories": ["冷知识/推荐"]
    }
  ],
  "entrance_hint": "入口建议",
  "total_duration_min": N,
  "skipped_events": ["因时间不够放弃的活动"],
  "post_visit_tips": ["离馆后建议"]
}
```

### Part 2: 自然语言攻略
按时间线输出，每站写明到达时间、必看内容、活动提醒、注意事项、趣味推荐。语气亲切自然，像朋友在现场带你逛。"""
```

**为什么要同时输出 JSON 和文案**：JSON 是给 Step 4 代码校验用的，文案是给用户看的。如果校验发现问题，只需要让 LLM 修正 JSON 对应的部分，不用重新生成整篇文案。

### 3.5 Step 4 详细设计：代码校验

对 LLM 输出的 Plan JSON 做确定性校验：

```python
def validate_plan(plan: dict, constraints: dict) -> list[str]:
    errors = []
    
    stops = plan["stops"]
    for i, stop in enumerate(stops):
        # 1. 时间线连续性
        if i > 0:
            prev = stops[i-1]
            expected_arrive = prev["depart_time"] + travel_time(prev["zone_id"], stop["zone_id"])
            if stop["arrive_time"] < expected_arrive:
                errors.append(f"站点{i+1}到达时间早于可能的最早时间")
        
        # 2. 闭馆冲突
        for closure in constraints["closures"]:
            if stop["zone_id"] == closure["zone_id"]:
                if time_overlap(stop["arrive_time"], stop["depart_time"],
                               closure["start"], closure["end"]):
                    errors.append(f"站点{i+1}与{closure['zone_name']}闭馆时段冲突")
        
        # 3. 回头路检测
        if i >= 2:
            floors = [get_floor(s["zone_id"]) for s in stops[i-2:i+1]]
            if floors[0] < floors[1] > floors[2] or floors[0] > floors[1] < floors[2]:
                errors.append(f"站点{i-1}~{i+1}出现回头路")
    
    # 4. 总时间检查
    if plan["total_duration_min"] > constraints["time_budget"] * 1.05:
        errors.append(f"总时间{plan['total_duration_min']}min超出预算{constraints['time_budget']}min")
    
    return errors
```

**校验结果处理**：

```
通过（95%+ 情况）→ 直接返回文案给用户
不通过 → 将错误信息附加到 prompt，再调一次 LLM 修正
```

### 3.6 数据结构

```python
@dataclass
class PlanStop:
    zone_id: str                  # 区域ID
    zone_name: str                # 区域名称
    arrive_time: str              # 到达时间 "HH:MM"
    depart_time: str              # 离开时间 "HH:MM"
    duration_min: int             # 停留分钟
    artifacts: list[str]          # 必看文物名称
    anchor_event: str | None      # 该站的时间锚点事件
    stories: list[str]            # 附着的趣味内容
    notices: list[str]            # 该站的注意事项

@dataclass
class Plan:
    stops: list[PlanStop]         # 有序站点列表
    entrance_hint: str            # 入口建议（如"走东门"）
    total_duration_min: int       # 总时长
    skipped_events: list[str]     # 时间不够放弃的事件
    post_visit_tips: list[str]    # 离馆后建议（如"今晚看国家宝藏"）
```

## 四、延迟分析

### 4.1 最终方案延迟

```
正常路径（95%+ 的情况）:
  Step 1 意图解析:    代码解析 ~0ms / 轻量LLM ~1s
  Step 2 并行检索:    N × aquery_data (并行) ~2s
  Step 3 LLM规划生成: 1次LLM调用 ~3-4s
  Step 4 代码校验:    ~10ms
  ────────────────────────────────
  总计: ~5-6s ✅

异常路径（校验不通过，< 5%）:
  正常路径 + LLM修正: ~5-6s + ~3s = ~8-9s ✅ 仍在 10s 内
```

### 4.2 LLM 调用次数对比

| 方案 | LLM 调用次数 | 总延迟 |
|------|:---:|:---:|
| 串行 4 轮（初始方案） | 4(关键词) + 4(生成) + 1(编排) = 9 次 | ~19s |
| 全部 LightRAG | 1(关键词) + 1(生成) = 2 次 | ~5-6s |
| 并行检索 + 纯代码编排 | N(关键词) + 1(生成) = 2-5 次 | ~5-6s |
| **最终方案** | **N(关键词) + 1(规划生成) = 2-5 次** | **~5-6s** |

最终方案与"全部 LightRAG"延迟相当，但效果和扩展性远优。

## 五、检索层与编排层的责任边界

| | LightRAG 检索层 | Agent 编排层 |
|---|---|---|
| **调用方式** | `aquery_data()` 纯检索，不触发 LLM 生成 | 调用 LightRAG 获取数据，自行调 LLM |
| **核心能力** | 向量检索 + 图遍历 + 关键词提取 | 意图解析、LLM 规划、代码校验 |
| **并发** | 支持多用户 + 同用户多查询并行（async，查询路径无锁） | 发起并行查询，等待全部返回 |
| **输出** | 结构化数据：entities, relationships, chunks | Plan JSON + 自然语言攻略 |
| **不做** | 不做规划、不做个性化、不做取舍 | 不做存储、不做向量计算、不做图遍历 |
| **扩展方式** | 换 workspace 切换博物馆 | 换 prompt 适配不同场景（规划/问答/导航） |

### 与其他文档的关系

- `museum_kg_design.md`：定义图谱的**数据结构**（节点、边、chunk 格式）→ 检索层的基础
- `museum_scenario_walkthrough.md`：定义攻略的**输出规范**（15个"活的"瞬间）→ 编排层的目标
- 本文档：定义**生成过程**（怎么从数据到攻略）→ 检索层和编排层的协作协议
