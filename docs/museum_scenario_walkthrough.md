# 端到端场景拆解：大众游客的 3 小时

> 本文档从用户视角走完一遍完整体验，拆解每个"活的"瞬间背后的检索逻辑，反过来验证和定型图谱设计。

## 一、场景设定

**用户画像**：小王，28 岁，第一次来国博，周六上午 9:00 到达，下午有约，只有 3 小时。

**用户输入**：
> "我第一次来国博，有 3 个小时，帮我规划一下怎么逛最值？"

**Agent 目标**：生成一份"活的"3 小时攻略——不是静态推荐路线的复读，而是叠加了当天活动、实时风险、趣味内容的个性化方案。

---

## 二、Agent 的 4 轮检索编排

Agent 收到用户意图后，不是一次查完所有东西，而是分 4 轮检索，每轮有明确的目的。前一轮的结果会影响后一轮的查询。

### 总览

| 轮次 | 目的 | 查询关键词 | 期望命中的节点类型 | 期望命中的边类型 |
|:----:|------|-----------|-----------------|----------------|
| R1 | 路线骨架 | "3小时 首次 国宝 精华路线" | Route, Zone, Artifact, Exhibition | ROUTE_STOP, DISPLAYED_IN, HOSTED_IN, ADJACENT_TO |
| R2 | 事件叠加 | "今天 活动 讲解 导览 工作坊" | Event | HAPPENS_AT→Zone, ABOUT→Artifact |
| R3 | 风险规避 | "今天 关闭 维修 限流 排队" | Notice | AFFECTS→Zone/Exhibition/Facility |
| R4 | 体验丰富 | "咖啡 文创 冷知识 打卡 拍照" | Story | HAPPENS_AT→Zone, ABOUT→Artifact/Theme |

## 三、R1：路线骨架——"3 小时怎么走？"

### 3.1 Agent 发起的查询

```
query: "3小时精华路线 首次来馆 必看国宝"
mode: hybrid (local + global)
```

### 3.2 LightRAG 检索过程

**向量检索**命中：
- Route chunk: `推荐路线「2小时国宝精华路线」：第1站B1北区（35分钟）→第2站B1南区（20分钟）→...`
- Theme chunk: `主题「商代青铜文明」：商代是青铜时代巅峰……文物分布在B1北区和F2南区`
- Exhibition chunk: `展览「庞贝神话」：来自意大利……建议参观时间25-40分钟`

**图遍历**命中：
- 从 Route(2小时国宝精华路线) 沿 `ROUTE_STOP` 边，取出 6 个途经站：
  ```
  B1北区(35min) → B1南区(20min) → F1北区(10min) → F1南区(15min) → F2北区(15min) → F3南区(25min)
  ```
- 每个 Zone 沿 `DISPLAYED_IN`（反向）拿到该站的亮点文物
- 沿 `ADJACENT_TO` 和 `ACCESSIBLE_BY_STAIRS` 拿到空间邻接关系和步行时间

### 3.3 Agent 拿到的原始骨架

| 站序 | 区域 | 时间预估 | 亮点文物 | 累计时间 |
|:----:|------|:-------:|---------|:-------:|
| 1 | B1北区 | 35 min | 后母戊鼎、四羊方尊、红山玉龙 | 0:35 |
| 2 | B1南区 | 20 min | 击鼓说唱俑、长信宫灯 | 0:55 |
| 3 | F1北区 | 10 min | 木雕观音 | 1:05 |
| 4 | F1南区 | 15 min | 粉彩转心瓶、钧窑尊 | 1:20 |
| 5 | F2北区 | 15 min | 真赏斋图、乾隆南巡图 | 1:35 |
| 6 | F3南区 | 25 min | 庞贝壁画、维纳斯雕像 | 2:00 |

**注意**：这是 2 小时路线，但小王有 3 小时。Agent 判断还有约 60 分钟的余量可以分配给活动、休息和额外展厅。这个判断由 Agent 做，不是 LightRAG 的职责。

### 3.4 Agent 的初步决策

- 基础路线 2 小时 + 60 分钟余量
- 余量分配方案待 R2-R4 结果后确定
- 路线从 B1 开始逐层上升，不走回头路（空间拓扑已通过 `ADJACENT_TO` 验证）

## 四、R2：事件叠加——"今天有什么活动？"

### 4.1 Agent 发起的查询

```
query: "2026-04-05 今天 活动 讲解 导览 体验"
mode: hybrid
filter: file_path LIKE 'museum:dynamic:event:%'
```

Agent 用 `file_path` 前缀过滤，只检索 Event 类型的动态节点。

### 4.2 LightRAG 检索过程

**向量检索**命中（按相关度排序）：
1. Event chunk: `【2026-04-05 10:00/14:00/16:00｜B1北区｜活动·guided_tour】B1北区青铜器志愿者讲解：……相关文物：后母戊鼎、四羊方尊、大盂鼎`
2. Event chunk: `【2026-04-05 14:00-15:00｜F3南区｜活动·guided_tour】庞贝特展策展人导览：张教授……限30人，剩余12名额`
3. Event chunk: `【2026-04-05 09:30-11:30｜F1北区｜活动·workshop】周末亲子工作坊：小小考古学家……限6-12岁`
4. Event chunk: `【2026-04-01~04-30｜游客接待台｜活动·stamp_rally】春季集章活动：寻找国宝守护者……集满6枚兑换徽章`

**图遍历**：
- Event(青铜器志愿者讲解) → `HAPPENS_AT` → Zone(B1北区)
- Event(青铜器志愿者讲解) → `ABOUT` → Artifact(后母戊鼎), Artifact(四羊方尊), Artifact(大盂鼎)
- Event(庞贝策展人导览) → `HAPPENS_AT` → Zone(F3南区)
- Event(庞贝策展人导览) → `ABOUT` → Exhibition(庞贝神话)
- Event(集章活动) → `HAPPENS_AT` → Zone(游客接待台)

### 4.3 Agent 交叉编织——"活"的瞬间 #1

Agent 发现 R2 结果与 R1 骨架有**空间重叠**：

| 事件 | 发生区域 | 时间 | 与路线的关系 |
|------|---------|------|------------|
| 青铜器志愿者讲解 | B1北区 | 10:00场 | **第1站**恰好是B1北区！9:00入馆，走到B1北区约9:05，等到10:00听讲解 |
| 庞贝策展人导览 | F3南区 | 14:00 | 第6站是F3南区，但小王12:00要离开，赶不上 |
| 亲子工作坊 | F1北区 | 09:30 | 面向6-12岁儿童，**受众不匹配**，过滤掉 |
| 集章活动 | 游客接待台 | 全天 | 入馆时顺手领集章册，**零成本叠加** |

**Agent 决策**：
- 调整第1站：B1北区从 35min 扩展到 55min（9:05 到达 → 先自行浏览 → 10:00 蹭讲解 40min → 10:45 离开）
- 集章活动：在入馆时经过游客接待台领取集章册，边逛边盖章
- 庞贝导览：时间不合，放弃（但提一句"如果下午有空可以回来"）
- 余量从 60min 减少到 40min（讲解多用了 20min）

**这就是"活的"逛馆体验**：不是"B1北区看35分钟"，而是"9:05先自己看看后母戊鼎，9:55到入口集合，10:00跟着志愿者老师听40分钟青铜器讲解，听完你对四羊方尊的理解会完全不一样"。

## 五、R3：风险规避——"今天有什么要注意的？"

### 5.1 Agent 发起的查询

```
query: "2026-04-05 关闭 维修 限流 排队 注意"
mode: hybrid
filter: file_path LIKE 'museum:dynamic:notice:%'
```

### 5.2 LightRAG 检索过程

**向量检索**命中：
1. Notice chunk: `【2026-04-05 15:00-16:00｜B1北区｜注意·hall_closure】B1北区临时闭厅：因展品维护……影响展品：后母戊鼎、四羊方尊……`
2. Notice chunk: `【2026-04-05 10:00-12:00｜全馆｜注意·queue_status】当前西门排队约20分钟，东门约8分钟……全馆客流80%`
3. Notice chunk: `【2026-04-05~04-06｜F2南区｜注意·facility_status】F2南侧电梯维修中……请使用北侧电梯或楼梯`
4. Notice chunk: `【2026-04-05~08-31｜F3南区｜注意·closing_soon】庞贝特展倒计时：还剩148天`

**图遍历**：
- Notice(B1北区临时闭厅) → `AFFECTS` → Zone(B1北区), Exhibition(古代中国·史前至南北朝)
- Notice(排队信息) → 无 Zone 关联（全馆性公告）
- Notice(电梯维修) → `AFFECTS` → Zone(F2南区)
- Notice(庞贝倒计时) → `ABOUT` → Exhibition(庞贝神话)

### 5.3 Agent 交叉编织——风险分析

| 风险 | 影响区域 | 影响时段 | 与路线的冲突 | Agent 对策 |
|------|---------|---------|------------|----------|
| B1北区临时闭厅 | B1北区 | 15:00-16:00 | 小王 9:05-10:45 在 B1 北区，**不受影响** | 无需调整，但告知用户"下午3点B1北区会关闭" |
| 西门排队 20min | 入口 | 上午高峰 | 小王 9:00 到达 | **建议从东门入馆**，省 12 分钟 |
| F2南侧电梯维修 | F2南区 | 全天 | 路线经过 F2 北区，但 F2 南区(玉器)不在基础路线中 | 如果余量时间想去 F2 南区，**提醒用北侧电梯** |
| 庞贝倒计时 | F3南区 | 长期 | 已在路线中 | 在推荐里**强调"限时展览"增加紧迫感** |

**Agent 决策**：
- 入口选择：东门而非西门（省 12 分钟排队）
- 路线不变：B1北区的闭厅时段（15:00-16:00）不影响上午的行程
- 电梯提示：记录备用，如果 Agent 后续在余量时间推荐 F2 南区，会附带提醒
- 庞贝紧迫感：在 F3 南区的推荐文案中加入"展到8月底就撤了"

**"活"的瞬间 #2**：如果小王说"我下午想再来一趟"，Agent 能立即回答"下午3点到4点B1北区关闭维护，如果你要看后母戊鼎得避开这个时段"——这种实时感来自 Notice 节点。

## 九、图谱设计的验证结论

通过走完这个端到端场景，我们可以验证以下设计决策是否成立：

### ✅ 验证通过的设计

| 设计决策 | 在场景中的验证 |
|---------|-------------|
| 动态节点分 Event/Notice/Story 三类 | R2/R3/R4 分别检索，互不干扰，每类有清晰的语义角色 |
| `HAPPENS_AT` 边连接到 Zone | Agent 能直接判断事件/内容在路线的哪一站，实现空间匹配 |
| `AFFECTS` 边连接到 Zone/Exhibition/Facility | 风险信号精确定位到具体区域，Agent 能判断是否影响当前路线 |
| `ABOUT` 边连接到 Artifact/Exhibition/Theme | 内容与文物关联后，Agent 能在看文物时推送相关冷知识/活动 |
| 不需要动态→动态边 | 瞬间5和瞬间6通过共享 Artifact(后母戊鼎) 隐式关联，无需显式边 |
| chunk 前缀带时间+地点+类型 | 向量检索能同时匹配语义("活动 讲解")和时空("2026-04-05 B1北区") |
| `file_path` 编码 `museum:dynamic:{type}:{date}` | Agent 可以按类型过滤，R2只搜Event、R3只搜Notice、R4只搜Story |
| `priority` 映射到边权重 | 高优先级的 Notice(闭厅 priority=4) 比低优先级的 Story(冷知识 priority=1) 更容易被检索到 |
| Route 节点带 `stop_order` 和 `duration_min` | Agent 直接用这些数据构建时间预算表，不需要自己算 |
| 3 类动态节点覆盖全部 7 个 JSON category | 20 个动态 item 无一遗漏，全部有对应的节点类型 |

### 💡 场景揭示的关键设计洞察

1. **4 轮检索的顺序不能乱**：R1 给骨架 → R2 叠加事件可能改变时间分配 → R3 避险可能改变空间路径 → R4 在确定的路线上锦上添花。如果先做 R4 再做 R1，冷知识无法匹配到站点。

2. **"活"的本质是交叉编织**：单独的 Event/Notice/Story 节点只是原材料。真正让体验"活"起来的是 Agent 把 R2 的讲解时间嵌入 R1 的路线骨架、把 R4 的冷知识插在 R2 讲解之后、把 R3 的排队信息前置到入口选择。这种编织是 Agent 的职责，LightRAG 只需要提供精准的候选数据。

3. **过滤能力是必需品，不是锦上添花**：
   - 受众过滤：亲子工作坊(target_audience=family) 被过滤掉
   - 时间过滤：庞贝策展人导览(14:00) 超出小王的时间窗口
   - 空间过滤：Event 的 Zone 与路线站点匹配

4. **"零成本叠加"是最优雅的推荐**：集章活动、AI导览、打卡机位都不需要额外时间或金钱投入，只需要在路线动线上"顺手做"。Agent 能识别这种零成本叠加机会，靠的是 `HAPPENS_AT` 边将动态节点锚定到了空间拓扑上。

## 十、检索与 Agent 的完整责任边界

| | LightRAG 知识层（本文档关注） | Agent 编排层（后续实现） |
|---|---|---|
| **输入** | 结构化查询 + 过滤条件 | 用户自然语言意图 |
| **处理** | 向量检索 + 图遍历 | 意图解析 → 4轮检索编排 → 交叉编织 → 过滤(受众/时间/空间) → 时间预算分配 → 路线优化 |
| **输出** | 候选节点 + 边 + chunk 文本 | 自然语言攻略（带时间线、提醒、冷知识） |
| **不做** | 不做意图理解、不做过滤、不做编排 | 不做存储、不做向量计算、不做图遍历 |
| **质量关键** | chunk 的向量质量、图的连通性、边的完整性 | 交叉编织的精度、推荐的自然度、时间预算的合理性 |

这个边界清晰意味着：LightRAG 可以被任何 Agent 框架调用（LangChain, AutoGen, 自研），只要 Agent 理解 4 轮检索协议和 `file_path` 过滤约定。
